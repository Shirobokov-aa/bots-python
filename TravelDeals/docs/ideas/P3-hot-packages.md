## Зачем

Сейчас `/tour` = zip авиа + отель (Travelpayouts). Готовый пакет (перелёт + отель + часто трансфер/страховка) часто дешевле «собрать самому» и даёт другой CPA-контур. Горящие = короткий горизонт вылета + жёсткие фильтры — контент для канала и режим поиска в боте без нового продукта.

## Как выглядит для юзера

**Бот**

> /tour горящие  
> откуда: Москва · бюджет до 60 000 · all inclusive · без визы · вылет ≤ 3 дней  
> → 3 пакета со ссылкой на бронь (Level.Travel / аналог)

**Канал**

> Горящий пакет · Анталья  
> вылет послезавтра · AI · без визы · от **52 000 ₽**/чел  
> [Смотреть пакет]

Тон как у M1: инфо, не крик «успей!!!».

## Что сделать

- [ ] Закрыть живой MVP TravelDeals (token/marker/канал уже в прогоне)
- [ ] Выбрать **один** пакетный провайдер на старт (кандидаты: Level.Travel → Sletat / Travelata)
- [ ] Партнёрка / API: ключ, deeplink с marker/sub_id, условия CPA
- [ ] Модель результата: цена/чел, даты, отель★, питание, виза, состав пакета
- [ ] Фильтры (минимум): вылет ≤ N дней (дефолт 3), бюджет ceiling, all inclusive, без визы
- [ ] Бот: режим «горящие» поверх `/tour` (не отдельная команда-продукт)
- [ ] Канал: опц. рубрика/порог для автопостов пакетов (рядом с M1)
- [ ] Маркировка рекламы (C4), если оффер не под тем же Travelpayouts ЕРИР

## Критерий «готово»

Юзер в боте получает ≥1 реальный пакет по фильтрам с рабочей партнёрской ссылкой; опционально такой же оффер уходит в канал без дублей. Zip авиа+отель остаётся fallback, пока провайдер молчит.

## Риски / зависимости

- **После MVP** — не начинать, пока Travelpayouts-контур нестабилен
- Доступ к API/партнёрке Level.Travel (или запасной) — без ключа только витрина-заглушка
- Состав «пакета» разный у провайдеров (трансфер/страховка не всегда в цене)
- Юр. маркировка: отдельный партнёр ≠ автоматически Travelpayouts C4
- Не плодить второго бота / канал только под пакеты
